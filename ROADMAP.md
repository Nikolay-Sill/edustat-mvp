# EduStat MVP — план реализации по этапам

MVP разбит на 8 этапов. Этап — логически законченный кусок работы, а не срок: каждый этап заканчивается работающим
результатом, который можно показать. Порядок повторяет сценарий 1 из раздела 5.6
документации: данные → прогноз → группа риска → работа со случаем → отчётность.

Обозначения: **FR** — функциональное требование из Таблицы 3.1,
**US** — пользовательская история из раздела 3.2,
**API** — метод из `edustat-openapi.yaml`.

## Этап 2. Загрузка данных из «LMS»

**Требования:** FR-01, FR-02, FR-03
**Задачи:**
- [ ] Скачать OULAD в `data/raw/`, разобрать структуру таблиц
- [ ] Сопоставить OULAD с моделью данных:

  | OULAD | EduStat |
  |---|---|
  | `courses` (code_module + code_presentation) | `academic.subject`, `lms_course_id` |
  | `studentInfo` / `studentRegistration` | `academic.student` (`lms_external_id` = id_student), синтетические группы и ФИО |
  | `studentVle` (клики по дням) | `integration.activity`; `sum_click` → число действий, `duration_sec` = NULL |
  | `vle.activity_type` | `activity_type` (свести к 5 значениям из спецификации) |
  | `assessments` + `studentAssessment` | `integration.exam_result` (TMA/CMA → TEST/CONTROL_WORK, Exam → EXAM, `max_score` = 100) |
  | `studentInfo.final_result` (Fail / Withdrawn) | целевая переменная для модели, в БД не грузится |

- [ ] Мок-коннектор: отдаёт данные OULAD порциями «по дням курса», чтобы загрузка была инкрементальной (FR-01)
- [ ] Запись в `integration.sync_job` (RUNNING → SUCCESS / FAILED, `records_loaded`)
- [ ] Очистка: пропуск дублей по `lms_record_id`, сопоставление по `lms_external_id`, ошибочные записи в журнал (FR-03)
- [ ] `POST /sync-jobs` (ручной запуск, FR-02), `GET /sync-jobs` (журнал)

**Готово, когда:** повторный запуск синхронизации не создаёт дублей, в журнале видно число загруженных записей.

## Этап 3. Метрики и обучение модели

**Требования:** FR-06, NFR-16, NFR-17
**Задачи:**
- [ ] Рассчитать метрики по паре «студент — дисциплина» (FR-06): средний балл в % от максимума, доля сданных заданий, активность за 7 и 14 дней, падение активности
- [ ] Зафиксировать «дату среза» (например, 60-й день курса), чтобы признаки не заглядывали в будущее — это имитирует прогноз за 1–2 месяца до сессии
- [ ] Ноутбук `ml/notebooks/train.ipynb`: обучение CatBoost, разбиение по презентациям курса (обучение на 2013, проверка на 2014 — аналог «прошлого семестра»)
- [ ] Посчитать ROC-AUC и recall для HIGH, сравнить с NFR-16 (≥ 0,80 и ≥ 0,75)
- [ ] Сохранить модель, записать версию в `analytics.model_version` (ограничение NFR-17 уже есть в схеме)

**Готово, когда:** в ноутбуке есть честные метрики качества на отложенной выборке. Если ROC-AUC < 0,80, это тоже результат — записать в `docs/deviations.md` с причиной.

**Требования:** FR-13, FR-14, FR-15, FR-16, FR-17
**Задачи:**
- [ ] При переходе в HIGH создавать `risk_case` и уведомление в кабинете (FR-13); e-mail — вне MVP
- [ ] Если по паре уже есть открытый случай — не дублировать уведомление, обновить карточку (US-02, критерий 2)
- [ ] `GET /risk-cases`, `PATCH /risk-cases/{id}`: смена статуса, мера, комментарий (FR-14)
- [ ] Переходы статусов строго по Таблице 4.2: NEW → IN_PROGRESS | FALSE_POSITIVE; IN_PROGRESS → RESOLVED | ESCALATED | FALSE_POSITIVE; ESCALATED → RESOLVED; недопустимый переход → 409 Conflict
- [ ] Автоматическое закрытие: риск снизился до LOW/MEDIUM → RESOLVED; при закрытии заполняется `closed_at`
- [ ] Передача в деканат и ложное срабатывание — только с комментарием (FR-15, FR-17; проверка есть и в БД)
- [ ] Деканат видит эскалированные случаи и фиксирует решение (FR-16)
- [ ] `GET /notifications`, `PATCH /notifications/{id}` (прочитано)

**Готово, когда:** можно пройти полный путь случая риска из диаграммы 4.4 через API.

## Стартовый список для `docs/deviations.md`

Уже найдено при восстановлении DDL — это хороший материал для собеседования:

1. **Факторы прогноза (FR-09)** есть в API (`Prediction.top_factors`), но не хранятся в ER-модели → добавлена таблица `analytics.prediction_factor`.
2. **Уведомления и отчёты** есть в API, но не в ER-модели (относятся к Notification и Reporting Service) → добавлены в V2.
3. **Связь «случай риска → студент и дисциплина»** в `risk_case` только через `prediction_id`. Чтобы проверить «один открытый случай на пару» (US-02), нужен join с `prediction`; возможно, стоит денормализовать `student_id` и `subject_id`, как в схеме `RiskCase` в API.
4. **Решение деканата (FR-16)** пишется в то же поле `comment`, что и комментарий преподавателя при эскалации, — комментарий преподавателя затирается. Варианты: отдельное поле `dean_decision` или таблица истории изменений случая.
5. **`duration_sec`** в OULAD отсутствует → метрика «часы в LMS» заменяется числом действий.
